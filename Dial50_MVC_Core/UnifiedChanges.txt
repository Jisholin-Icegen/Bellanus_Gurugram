Unified AI changes and AI-team integration
==========================================

Purpose
-------
The Home page owns the voice WebSocket. Unified service pages load in an iframe
and reuse that Home connection; navigating between service pages must not open
another socket. Page controls, service categories, menu items, and notification
records are read from the current page or the existing tenant database. Do not
hardcode patient, tenant, category, menu, or notification values in the AI.

Connection and status
---------------------
The voice client requests one access token per explicit call start. A failed
token request, including HTTP 429, ends that attempt and is never retried
automatically; the user must explicitly start another call to request a new
token. WebSocket reconnects reuse the call's existing token and use exponential
backoff capped at 15 seconds. The voice service must accept that token for a
reconnect; the client will not request another token in the same call. It keeps
the call timer running and reuses a live microphone stream, reacquiring it if
the browser ended the track. Calls have no default time limit; a positive
SESSION_SECONDS value in APP_CONFIG can still set an explicit limit. The
persistent assistant bar shows the same Connecting, Reconnecting, Listening,
Thinking, or Speaking status as the Home call screen while the call is
connecting or connected.
The assistant bar remains above the unified page frame. Go to Chat only hides
that frame and returns to the Home call screen; it must not end or recreate the
voice socket. The explicit End Call control, a valid server call_ended event,
or an unrecoverable call-start failure ends the session.

This client-side reconnect does not replace a healthy voice backend. The AI
team must keep its server-side voice session valid, accept the existing token
during a reconnect, and send/receive the JSON action messages below over the
socket. A successful token response or health check does not prove that the
WebSocket and audio session are stable; a full speech round-trip must be
verified against the configured voice service.

WebSocket contract
------------------
The app sends:

  {"type":"app_context","context":{...}}

Context is refreshed as the visible page and its dynamic content change. It
includes the current route/title/headings, visible buttons/actions, form fields,
dropdown controls and options, checkboxes/radio choices, and relevant dynamic
page items. Action/field/choice target IDs are temporary: use them only from the
latest context. Patient identifiers are redacted from context text where
recognized. Tenant IDs and database connection strings are not AI context.

The AI sends one flat action envelope (do not nest the action object):

  {"type":"app_action","action":"navigate","target":"room_comfort","request_id":"r1"}

The app returns:

  {"type":"app_action_result","request_id":"r1","success":true,"result":{},"error":null}

Always include a unique request_id and wait for the corresponding result before
claiming a write succeeded. An error result means the app did not confirm the
requested action.
For ui.click, the app refreshes visible page context after the click before
returning success, so follow-up actions can use newly visible controls such as
the Nutrition modal's Done button.

Actions
-------
Generic visible controls:

  ui.click       targetId from latest context
  ui.fill        targetId, value
  ui.select      controlId, optionValue
  ui.set_choice  targetId, checked (boolean)
  navigate       target or same-site path

Requests:

  {"type":"app_action","action":"request.options","module":"room_comfort","request_id":"r2"}
  {"type":"app_action","action":"request.create","module":"room_comfort","categoryId":"<live id>","category":"<live name>","quantity":1,"remarks":"<spoken details>","request_id":"r3"}

Supported request modules are room_comfort, logistics, and food_other_services.
Call request.options first and use its current category ID/name; ask the patient
to clarify if a request does not match exactly one live category. The app maps
request.create to its existing page/controller flow, fills the remarks and
quantity fields, submits, and reports the resulting request number. Use the
same request actions for Room Comfort, Logistics, and Food Dining > Other
Services. Do not call another site's RequestcreationAPIReq endpoint from the
browser or voice service.

Food ordering:

  food.intent             intent: explore or order
  food.select_order_type  orderType: patient or visitor
  food.select_mode        mode: now or preorder
  food.select_meal        meal from the live meal list
  food.select_vendor      vendor from the live dropdown
  food.select_diet        diet from the live dropdown
  food.select_language    language from the live dropdown
  food.list_menu          returns current menu items
  food.add_item           itemId (or exact unique itemName), meal, quantity
  food.set_quantity       itemId, meal, quantity (0 through 20)
  food.remove_item        itemId, meal
  food.review_order       prepares the review page
  food.submit_order       submits the current cart
  food.other_service      legacy categoryId/remarks action for Other Services

The AI must choose menu IDs and meal/vendor/diet/language options from the
latest live context or list response. It may send spoken food instructions as
specialInstructions or remarks; those are placed into the menu instructions
field and included with order submission. If food.submit_order arrives on the
menu page, the app prepares Review Order, restores the action request ID, and
submits the current cart there. If there is no cart, the app returns an error.
Patient menu responses omit item prices; visitor responses may include them.
The patient-facing review screen hides visitor-only costs.

Notifications:

  notification.list          loads the current room's live notifications
  notification.mark_read     notificationId from the latest list
  notification.mark_all_read
  notification.open          notificationId from the latest list

Opening a notification marks it read when necessary and navigates to its
associated order/request page. Mark-read actions change app data; only perform
them when requested by the patient.

Feedback:

  feedback.start
  feedback.answer  questionId/departmentId and value (optional remarks)
  feedback.submit

Feedback questions and choices are loaded from the current tenant. The app
rejects incomplete or invalid submissions.

Notification permission prompt
------------------------------
Supported browsers show one app prompt with Allow Notifications and Maybe
Later. Allow requests browser permission from the user's click and saves a
push subscription for that browser. Browser permission is inherently per
browser/device. Maybe Later is stored server-side for 12 hours and is shared
across the room's pages and browsers; local storage also prevents repeated
prompts across tabs in the same browser. Unsupported browsers and browsers
whose notification permission is already denied do not show a prompt. The app
does not ask users to install the site or add it to the home screen.

My Daily Care
-------------
The page keeps its four existing cards. My Library remains the only
touch-enabled card. On the standalone page, touching it opens the legacy
assistant confirmation and starts the page's video assistant; inside Unified AI,
it returns to the persistent Home voice assistant instead of creating another
voice connection. The AI can navigate to service routes by voice without
enabling the other three cards or changing the Home assistant layout.

Active call window
------------------
The existing floating assistant popup is the minimized call UI; there is no
separate minimize window or extra control. Pressing the call screen's Back
button or navigating to another module hides the full call screen, restores the
same Home layout used before the call, and shows the popup while the call stays
active. Ending or failing a call while minimized does not restore the full call
screen over Home. The Home AI card and the popup's return/chat control both
restore the full call screen and hide the popup. A voice route to Home returns
to the Home layout with the popup still active. Hiding the page also minimizes
the screen. The call stays active until the user selects End Call; remote
disconnects reuse the current token when reconnecting.

Tenant and data handling
------------------------
Unified navigation preserves BedInfo, XTenantID, and region. TenantProvider
accepts the correctly spelled XTenantID parameter and the legacy XTenentID
alias. In multi-tenant mode, a missing or unresolved tenant now fails instead
of silently falling back to the default tenant database. Tenant-mode and
tenant-connection lookups are cached for five minutes to avoid repeating the
central-database lookup on each request. Do not put tenant IDs, database
connection strings, or patient identifiers into AI prompts or logs.

Local smoke test
----------------
Use:

  https://localhost:7116/PreLanding?BedInfo=9330&region=SA&XTenantID=2

To open the local-only Unified AI action panel, add `UnifiedAITest=1` to the
Home URL, for example:

  https://localhost:7116/Home/Index?BedInfo=9330&region=SA&XTenantID=2&UnifiedAITest=1

The test panel is available only on localhost and does not create a voice
connection. Its simulated session exercises page context, navigation, and
visible app actions. Actions that can change application data require an
additional confirmation; only run them against a confirmed test database.
Start Talk to AI separately to test the real voice service and speech round-trip.

The supplied local tenant/database must be verified as test data before writes.
Exercise each configured tenant and the voice service separately; a local build
cannot establish that every production tenant database or external AI service
is healthy.
